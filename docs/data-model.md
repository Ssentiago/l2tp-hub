# Модели данных

Документ описывает структуры данных, хранение в SQLite, системную связку ключей и
шифрованный backup конфигурации.

## Модели

Основные структуры определены в `l2tp-hub-core/src/models`.

### Connection

Описание VPN-подключения. Ключевые поля:

| Поле | Тип | Назначение |
|------|-----|-----------|
| `id` | string | Уникальный идентификатор (UUID) |
| `service_name` | string | Имя сервиса, бывшее `name`, есть JSON-алиас |
| `display_name` | string | Отображаемое имя |
| `server` | string | Адрес VPN-сервера |
| `username` | string | Имя пользователя |
| `keychain_key` | string | Ключ пароля в связке ключей |
| `shared_secret_key` | string | Ключ общего ключа в связке ключей |
| `service_hash` | string | Хеш конфигурации для определения пересоздания |
| `labels` | map | Метки вида идентификатор на значение |
| `connect_count` | number | Счётчик подключений |
| `connected_since` | number | Момент текущего подключения (unix секунды) |
| `last_connected_at` | number | Последнее подключение |
| `last_disconnected_at` | number | Последнее отключение |
| `tunnel_mode` | string | Режим маршрутизации: `full` или `split` |
| `split_routes` | array | Подсети для split-туннеля в нотации CIDR |

Поле `service_name` ранее называлось `name`. Для совместимости оставлен алиас
`#[serde(alias = "name")]`, поэтому старые данные десериализуются корректно.

### Workspace

Рабочее пространство, группа подключений. Поля: `id`, `name`, `connections`,
`group_by`. Поле `group_by` задаёт уровни группировки дерева, по умолчанию
`["company", "branch"]`.

### Label

Метка для категоризации. Поля: `id`, `name`, `built_in`. Встроенные метки `company`
(Компания) и `branch` (Филиал) создаются по умолчанию и не удаляются.

### ConnectionPayload

Входные данные сохранения подключения. Содержит необязательный `id`, отображаемое имя,
сервер, пользователя, пароль, общий ключ, метки, режим туннеля и подсети. Пустые
`password` и `shared_secret` означают "оставить существующие значения".

### Store

Корневой объект состояния. Содержит список `workspaces`, `active_workspace_id` и
`labels`. Методы: `active_workspace`, `find_connection`, `all_connections` и их
варианты для мутации. Загружается и сохраняется через `store::load` и `store::save`,
обе функции асинхронные.

## Хранение в SQLite

База данных: файл `l2tp-hub.db` в директории данных приложения. Пул соединений
`sqlx` с `max_connections(4)` и `journal_mode=WAL`. Единая точка доступа: `db.rs`.

### Схема

Таблица `labels`: `id` (первичный ключ), `name`, `built_in`.

Таблица `workspaces`: `id` (первичный ключ), `name`, `group_by` (JSON-строка).

Таблица `connections`: `id` (первичный ключ), `workspace_id` (внешний ключ на
workspaces с каскадным удалением), `name`, `display_name`, `server`, `username`,
`keychain_key`, `shared_secret_key`, `service_hash`, `labels` (JSON), `connect_count`,
`connected_since`, `last_connected_at`, `last_disconnected_at`, `tunnel_mode`,
`split_routes` (JSON).

Таблица `settings`: `key` (первичный ключ), `value`. Хранит
`active_workspace_id`.

### Миграции

При создании таблиц колонки `tunnel_mode` и `split_routes` добавляются повторно через
`ALTER TABLE`, ошибка "колонка уже существует" игнорируется. Это простая эволюция
схемы без отдельного инструмента миграций.

При первом запуске на пустой базе выполняется миграция из старого JSON-файла
`connections.json` (формат Store или легаси-формат со списком подключений без
рабочих пространств).

### Стратегия сохранения

`save_store` перезаписывает состояние целиком в одной транзакции: удаляет все метки,
рабочие пространства и подключения, затем вставляет их заново из Store. Это простая
модель "снимок целиком", а не инкрементальные обновления. Это учитывается при работе
с большими объёмами и при конкурентном доступе.

## Связка ключей

Пароли и общие ключи не хранятся в базе. В базе лежат только имена ключей, сами
значения в системной связке ключей: Keychain на macOS, Credential Manager на Windows.

Сервис связки ключей: `com.sentiago.l2tp-hub`. Имена ключей: `password_{id}` для
пароля и `shared_{id}` для общего ключа, где `id` это идентификатор подключения.

Реализация в `l2tp-hub-core/src/keychain` разделена по платформам, используется
крейт `keyring`. Проверка доступа к связке выполняется записью и удалением тестовой
записи `_l2tp_hub_access_test`, что вызывает системный запрос разрешения.

## Шифрованный backup

Экспорт и импорт конфигурации с шифрованием реализованы в `src-tauri/src/backup.rs`.

Формат файла версии 2: сигнатура `L2TPHUB` (7 байт), версия формата (1 байт),
идентификатор KDF (1 байт), параметры KDF `m_cost`, `t_cost`, `p_cost` (по 4 байта,
порядок big-endian), соль (32 байта), nonce (12 байт), шифровотекст AES-256-GCM.

Вывод ключа. Ключ шифрования выводится из пароля через Argon2id (версия 0x13) со
случайной солью, параметры зафиксированы в заголовке файла (m_cost 19456 KiB,
t_cost 2, p_cost 1). Каждый экспорт использует новую соль и случайный nonce.

Состав экспорта. `make_backup` собирает подключения с открытыми паролями и общими
ключами из связки ключей и метки, сериализует в JSON и шифрует.

Импорт. `restore_backup` определяет формат по сигнатуре, расшифровывает (при ошибке
возвращает "Неверный пароль или файл повреждён"), записывает секреты обратно в
связку ключей и восстанавливает структуры. Импорт сливает подключения в активное
рабочее пространство по идентификатору.

Старые бэкапы версии 1 (сигнатура `L2TP-HUB`, ключ как один SHA-256 пароля без соли)
остаются читаемыми: они распознаются по сигнатуре и расшифровываются старым способом.
Новый экспорт всегда пишется в формате версии 2.

## Расположение данных

| Данные | Где хранятся |
|--------|-------------|
| База SQLite | `l2tp-hub.db` в директории данных приложения |
| Секреты | системная связка ключей |
| Зашифрованный экспорт | файл `.conf`, выбирает пользователь |
| Логи сессий | `session-logs/{id}/{timestamp}/` в директории данных |
| Активные конфиги | `/private/var/root/l2tp-hub/active` (root, chmod 700) |
| Состояние маршрутов | `/private/var/root/l2tp-hub/route.state` |
