# Жизненный цикл подключения

Документ описывает, как устанавливается и разрывается VPN-туннель: генерацию конфигов,
запуск демонов, мульти-подключения, управление маршрутами и режимы туннелирования.
Это самая сложная часть проекта.

## Общая схема

Туннель строится из трёх слоёв: strongSwan (charon) поднимает IPSec, xl2tpd поверх
него ведёт L2TP, pppd создаёт PPP-интерфейсы `pppN`. Управление идёт из ядра через
привилегированный исполнитель. Один charon и один xl2tpd обслуживают все активные
подключения одновременно.

## Генерация конфигов

Функции в `l2tp/macos/config.rs` создают конфигурационные файлы.

`generate_configs` (одиночное подключение) и `generate_merged_configs` (все активные)
пишут:

swanctl.conf. Конфигурация strongSwan в формате VICI. Секция `connections` с одним
блоком на подключение: IKEv1, PSK-аутентификация, transport mode для UDP 1701,
набор предложений шифрования. Секция `secrets` с общим ключом на подключение.

xl2tpd.conf. Секция `[global]` с портом 1701 и секция `[lac ...]` на каждое
подключение с адресом сервера, путём к ppp-опциям и настройками перезвона.

options-<name>.xl2tpd. Опции pppd: без сжатия и шифрования на уровне PPP, MTU и MRU
1400, аутентификация PAP с именем и паролем, явный `unit {idx}` для уникального
`pppN`.

strongswan.conf. Конфигурация charon: маршруты не ставятся автоматически, включено
логирование в файл.

ip-up и ip-down. Заглушки-скрипты, route management целиком выполняется из Rust.

## Запуск подключения

`L2tpManager::connect` в `manager.rs` это точка входа. Порядок:

1. Загружается подключение, проверяются правила режимов и пересечение подсетей.
2. Подключение помечается активным (при ошибке отметка снимается).
3. Из связки ключей читаются пароль и общий ключ.
4. `create_vpn_service` генерирует конфиги.
5. Вычисляется `service_hash`, при изменении он сохраняется.
6. Собирается `ConnData` для всех активных подключений.
7. Захватывается мьютекс `DAEMON_STARTUP` для сериализации запуска демонов.
8. Определяется, первое ли это подключение (по запущенности xl2tpd).
9. Вызывается `connect_vpn` с таймаутом 60 секунд.
10. Обновляется статистика подключения.

## Первое и последующие подключения

`connect_vpn` в `connect.rs` ведёт себя по-разному.

Первое подключение. Полный запуск: остановка старых демонов, очистка портов 500 и
4500, удаление pid-файлов, уничтожение устаревших PPP-интерфейсов. Затем деплой
конфигов, подготовка инфраструктуры xl2tpd (fifo control, `/etc/ppp/options`),
установка и запуск charon как LaunchDaemon, ожидание VICI-сокета до 15 секунд,
`swanctl --load-all`, установка и запуск xl2tpd.

Последующее подключение. Деплой merged конфигов, `swanctl --load-all`, затем полный
рестарт xl2tpd чтобы подхватить новый LAC. SIGHUP не перечитывает конфиг xl2tpd, так
что рестарт это единственный надёжный путь. После рестарта ожидается появление всех
`pppN` интерфейсов (по количеству подключений) до 30 секунд.

Ключевое отличие: charon не перезапускается при добавлении подключения, только
xl2tpd. Первый поднимающий определяет `is_first` по отсутствию процесса xl2tpd.

## PPP интерфейсы и синхронизация

Каждый LAC получает свой интерфейс `pppN`. Номер задаётся явно через `unit {idx}` в
опциях pppd, где индекс это позиция в отсортированном списке `all_conns`. Порядок
детерминирован: существующие подключения сортируются по id, новое добавляется в
конец. Это гарантирует стабильное назначение интерфейсов.

Синхронизация между параллельными подключениями идёт через `tokio::sync::Notify`
(`ppp_ready`). Первое подключение сигналит после создания `ppp0`, второе регистрирует
ожидание до проверки и продолжает по сигналу.

## Маршрутизация

Модуль `routes.rs` управляет системными маршрутами. Проблема: при full-туннеле VPN
забирает default route, поэтому `route -n get default` начинает врать. Решение:
физический маршрут захватывается до поднятия VPN.

`capture_physical_route` сохраняет пару (интерфейс, шлюз) до подключения.
`save_route_state` пишет состояние в `/private/var/root/l2tp-hub/route.state` в
формате: сервер, интерфейс, шлюз, режим туннеля, подсети через запятую. Это нужно
для восстановления после падения.

Выставление маршрутов. Для каждого подключения маршруты ставятся на его собственный
`pppN`. Всегда добавляется хост-маршрут до сервера через исходный шлюз. Для split
добавляются маршруты подсетей на PPP-интерфейс. Для full default route переключается
на PPP-интерфейс, затем проверяется ping, и при неудаче маршрут откатывается.

Восстановление. `restore_routes` при отключении удаляет хост-маршрут, для split
удаляет подсети, для full восстанавливает default route. `resolve_restore_gateway`
подбирает актуальный шлюз в три уровня: исходный интерфейс если ещё активен, сохранённый
шлюз если достижим, любой активный физический интерфейс. Это учитывает смену сети при
восстановлении.

## Режимы туннелирования

Full tunnel. Весь трафик через VPN. Default route указывает на PPP-интерфейс.
Эксклюзивен: нельзя подключить, если есть другие активные подключения.

Split tunnel. Через VPN идут только указанные подсети, интернет напрямую. Можно
держать несколько параллельных split-подключений, если их подсети не пересекаются.

Правила валидации в `L2tpManager::connect`: full блокируется при наличии активных
подключений, split блокируется при активном full, пересечение CIDR подсетей у разных
split-подключений блокирует подключение. Пересечение проверяется функцией
`routes_overlap`: две подсети пересекаются, если одна содержит другую.

Переключение на лету. `switch_tunnel_mode` меняет маршрут без переподключения: при
переходе в split удаляется VPN default и добавляются подсети, при переходе в full
подсети удаляются и default переключается на PPP.

## Отключение

`L2tpManager::disconnect` различает два случая.

Последнее подключение. Полная остановка через `disconnect_vpn`: останавливается
heartbeat, деактивируется guardian, `swanctl --terminate` рвёт SA, pppd получает
SIGTERM, останавливаются и удаляются LaunchDaemon'ы charon и xl2tpd, убиваются
процессы, восстанавливаются маршруты из сохранённого состояния, проверяется связь
ping, удаляются pid-файлы и активная директория.

Не последнее. `disconnect_single`: терминируется SA конкретного подключения,
удаляются его маршруты и конфиги, затем генерируется merged конфиг для оставшихся и
делается рестарт xl2tpd с повторным выставлением маршрутов.

В обоих случаях перед отключением сохраняются логи сессии.

## Статус туннеля

`status` и `all_statuses` определяют статус каждого подключения отдельно, по данным
его собственного туннеля. При генерации merged-конфигов каждому подключению пишется
маркер `ppp-unit` с номером его юнита (в каталог подключения). Статус проверяет
конкретный интерфейс `pppN` в состоянии UP + RUNNING и уточняет состояние по IPSec SA
из `swanctl --list-sas --raw` (имя секции — `sanitize_name(service_name)`): интерфейс
работает, значит подключено; интерфейса нет, но SA установлен, значит подключение;
иначе отключено. Глобальные процессы xl2tpd и pppd для статуса не используются.
Статусы: `Connected`, `Connecting`, `Reconnecting`, `Disconnected`, `Unknown`.

## Guardian и heartbeat

При первом подключении пишется PID приложения в `/tmp/l2tp/tauri.pid`, активируется
guardian с текущим состоянием маршрутов и запускается heartbeat-поток. Поток шлёт
`heartbeat` в guardian каждые 3 секунды. При отключении поток останавливается, guardian
деактивируется. Роль guardian как страховки описана в `daemons.md`.

## Ошибки подключения

При неудаче собираются признаки: код завершения pppd из лога xl2tpd, живность
демонов, состояние IKE SA из `swanctl --list-sas --raw`, строки логов charon и pppd.
`classify_connect_failure` по упорядоченной таблице правил выбирает стабильный код
ошибки и этап сбоя, структурные сигналы имеют приоритет над текстом логов. Код, этап
и признаки уходят в UI событием `vpn-status-changed` и через отклонение команды
`connect_vpn`, текст и подсказки для пользователя берутся по коду во фронтенде
(`src/core/connectErrors.ts`). Механизм классификации описан в `core-library.md`.
Логи сессии сохраняются в историю для диагностики. Перед остановкой туннеля
снимаются счётчики интерфейса pppN: трафик сессии пишется в `SessionMeta`
(`bytes_in`, `bytes_out`) и прибавляется к накопленной статистике подключения
(`total_uptime_secs`, `total_bytes_in`, `total_bytes_out`).

## Ключевые файлы логики

|------|-----------|
| `manager.rs` | Правила подключения, мульти-подключения, статусы |

| `config.rs` | Генерация конфигов |
